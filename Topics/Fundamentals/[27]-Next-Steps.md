# Lesson 27 - Next Steps

You've covered the fundamentals — now the challenge shifts from "learning to code" to "becoming the kind of developer someone wants to hire or work with." This lesson covers how to choose a direction, prove your skills through projects, and keep learning after the structured part of the course ends.

---

## 27.1 Choosing a Specialization

You don't need to specialize immediately, but at some point focusing deepens your skills faster than staying broad. Specializing doesn't mean you stop learning other things — it means you have a primary lane.

### How to choose
- **Follow energy, not just aptitude.** You'll likely be better long-term at what you're motivated to keep doing after work, not just what came easiest in class.
- **Sample before committing.** Build one small project in 2–3 areas before picking — a weekend is enough to know if something clicks.
- **Consider the job market in your region**, but don't let it override genuine interest — burnout from disliked work compounds over a career.
- **Look at adjacent skills.** Backend devs benefit from some DevOps; frontend devs benefit from some backend — specialization is a center of gravity, not a wall.
- **Revisit the choice periodically.** Specializations shift over a career; the goal now is a strong first direction, not a permanent one.

## 27.2 Building Projects & Portfolio

Projects are how you prove skill when you don't yet have professional experience — and they remain valuable throughout your career as evidence of what you can actually build.

### What makes a strong portfolio project
- **Solves a real (even small) problem** — not just a tutorial clone. "Todo app #47" doesn't stand out; a tool that solves *your own* annoying problem does.
- **Is finished, not perpetually "in progress."** A small, complete project beats a huge, half-built one.
- **Shows your reasoning**, not just the result — a good README explaining decisions and trade-offs is often more impressive than the code itself.
- **Demonstrates range over time** — 2–4 varied, polished projects usually beat 15 similar ones.

### Project ideas by goal
- **To learn a new skill:** Rebuild something you already understand (e.g., a URL shortener) using the new tech, so you can focus on the tool, not the problem.
- **To show initiative:** Build something that solves a problem for a specific audience (a Discord bot for your community, a script automating a tedious personal task).
- **To show depth:** Contribute a substantial feature to an open-source project instead of another solo build.

### What to include for each project
1. **Clear README** — what it does, why you built it, how to run it, tech used.
2. **Live demo link** if possible — recruiters rarely clone and run code locally.
3. **Screenshots/GIFs** for anything visual.
4. **Notable challenges and how you solved them** — this is what turns a project into a talking point in interviews.

### Presenting your portfolio
- A simple personal site or a well-organized GitHub profile README is enough — polish matters more than complexity.
- Pin your best repositories on GitHub so they're the first thing visitors see.
- Keep it updated — a portfolio with 2019 projects and nothing since signals stagnation.

## 27.3 Resources for Continued Learning

Learning doesn't stop after a course — the field moves fast, and continued growth is part of the job.

### Types of resources worth building a habit around
- **Official documentation** — always the most accurate source; get comfortable reading it directly rather than relying only on tutorials.
- **Changelogs / release notes** of tools you use — a fast way to stay current without noise.
- **Source code of libraries you depend on** — reading real, production code teaches patterns tutorials don't.
- **Newsletters/blogs curated for your stack** — lower-effort way to stay aware of trends and new tools.
- **Communities** (Discord servers, forums, local meetups) — useful for questions, accountability, and job leads.
- **Structured courses** — still valuable for filling specific gaps once you know what you don't know.
- **Conference talks** — often the fastest way to understand *why* a tool/pattern exists, not just how to use it.

### Habits that compound
- **Build something with every new concept you learn** — passive reading fades quickly; applied learning sticks.
- **Read other people's code regularly** — open source projects, coworkers' PRs, or code review are a constant source of new techniques.
- **Teach or write about what you learn** — explaining something (a blog post, a README, answering a forum question) reveals gaps in your own understanding.
- **Revisit fundamentals periodically.** Concepts like data structures, algorithms, and system design pay off more the more experience you have to apply them to.
- **Don't chase every new framework.** Depth in a smaller number of tools is usually worth more than shallow exposure to many.

---

## Key Takeaways
- **Specializing** gives you depth and direction — sample a few areas before committing, and expect the choice to evolve.
- **Projects** are your proof of skill — a few polished, well-documented projects beat many unfinished ones.
- **Continued learning** is a habit, not an event — build, read, and teach consistently rather than relying on one-off courses.

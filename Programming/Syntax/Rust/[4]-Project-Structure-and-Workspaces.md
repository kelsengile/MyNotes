# Lesson 4 - Project Structure And Workspaces

## 4.1 Standard Layout

A typical Cargo project follows this shape:

```
hello_rust/
├── Cargo.toml
├── Cargo.lock
├── src/
│   ├── main.rs      // binary entry point
│   └── lib.rs        // library code (optional)
├── tests/            // integration tests (optional)
└── target/           // build output (auto-generated, not committed)
```

- A crate with `src/main.rs` produces an executable **binary crate**.
- A crate with `src/lib.rs` produces a reusable **library crate**.
- A project can contain both — a `main.rs` that uses the logic defined in `lib.rs`.

Add `target/` to a `.gitignore` file — it's regenerated by the compiler and shouldn't be versioned.

---

## 4.2 Binaries vs. Libraries

Splitting logic into `lib.rs` and keeping `main.rs` thin is a common pattern: it lets your core logic be tested and reused independently of the command-line interface around it.

```rust
// src/lib.rs
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

```rust
// src/main.rs
use hello_rust::add;

fn main() {
    println!("{}", add(2, 3));
}
```

---

## 4.3 Multiple Binaries

A single crate can produce more than one executable by adding files under `src/bin/`:

```
src/
├── main.rs
└── bin/
    └── extra_tool.rs
```

Run a specific one with `cargo run --bin extra_tool`.

---

## 4.4 Workspaces

A **workspace** groups multiple related crates that share a single `Cargo.lock` and `target/` directory — useful for larger projects split into separate libraries and binaries. A workspace root `Cargo.toml` looks like:

```toml
[workspace]
members = [
    "core",
    "cli",
]
```

Each member (`core/`, `cli/`) is its own crate with its own `Cargo.toml`, but they all build together and can depend on one another:

```toml
# cli/Cargo.toml
[dependencies]
core = { path = "../core" }
```

Workspaces keep large, multi-crate codebases organized without needing separate repositories for every piece.

# Lesson 14 - Static And Media Files

---

## 14.1 Static files in development

Django separates two kinds of files that are not generated by your Python code:

| Kind | Examples | Who provides them |
|---|---|---|
| **Static files** | CSS, JavaScript, logos, fonts | **You**, the developer, as part of the project |
| **Media files** | Profile pictures, uploaded documents | **Users**, uploaded while the site runs |

Static files are part of your source code and are the same for everyone. Media files are data. Keeping the two apart matters for both organization and security.

### The staticfiles app

Static file handling is provided by `django.contrib.staticfiles`, which is installed by default:

```python
INSTALLED_APPS = [
    ...
    "django.contrib.staticfiles",
]
```

### Core settings

```python
# settings.py
STATIC_URL = "static/"
STATICFILES_DIRS = [BASE_DIR / "static"]
```

| Setting | Meaning |
|---|---|
| `STATIC_URL` | The URL prefix used to reference static files in the browser (`/static/...`) |
| `STATICFILES_DIRS` | Extra folders, beyond each app's `static/` folder, where Django looks for static files |

### Where Django finds static files

Django uses **finders** to locate files. By default it looks in:

1. Every folder listed in `STATICFILES_DIRS` (project-wide assets).
2. A `static/` folder inside each installed app (`AppDirectoriesFinder`).

A recommended layout:

```
mysite/
├── static/                  # project-wide assets
│   └── css/base.css
└── blog/
    └── static/
        └── blog/            # namespaced by app name
            ├── css/style.css
            └── js/app.js
```

**Namespace** app static files inside a folder with the app's name (`blog/static/blog/...`), just as with templates (Lesson 4). Otherwise two apps that both ship `style.css` will collide, and Django will silently use the first one it finds.

### Using static files in templates

```html
{% load static %}
<link rel="stylesheet" href="{% static 'css/base.css' %}">
<script src="{% static 'blog/js/app.js' %}"></script>
<img src="{% static 'blog/img/logo.png' %}" alt="Logo">
```

`{% static %}` builds the correct URL from `STATIC_URL`, so if you later move your files (for example to a CDN) you change one setting instead of editing every template. Remember that each template needs its own `{% load static %}`.

### How files are served during development

With `DEBUG = True` and `django.contrib.staticfiles` installed, the `runserver` command serves static files automatically. You do not need to configure URLs. After adding a new file you usually just refresh the browser.

If you are using a different development server, or a test setup, you can add the URLs manually:

```python
# mysite/urls.py
from django.contrib.staticfiles.urls import staticfiles_urlpatterns

urlpatterns = [
    ...
]
urlpatterns += staticfiles_urlpatterns()
```

### Troubleshooting

| Symptom | Likely cause |
|---|---|
| 404 for a static file | File is in the wrong folder, `STATICFILES_DIRS` is wrong, or the app is not in `INSTALLED_APPS` |
| Template shows `{% static %}` as text | Missing `{% load static %}` |
| Old CSS keeps showing | The browser cached it; do a hard refresh (`Ctrl + Shift + R`) |
| Wrong file served | Two apps share the same un-namespaced path |

To check where Django would find a file:

```bash
python manage.py findstatic css/base.css
```

### Linking to static files in CSS

Relative URLs in a CSS file are resolved relative to the CSS file itself, so images next to your stylesheet can be referenced simply:

```css
.logo {
  background-image: url("../img/logo.png");
}
```

## 14.2 Media uploads

**Media files** are files uploaded by users. They are handled separately from static files because they are created at runtime and must never be treated as trusted code.

### Settings

```python
# settings.py
MEDIA_URL = "media/"
MEDIA_ROOT = BASE_DIR / "media"
```

| Setting | Meaning |
|---|---|
| `MEDIA_ROOT` | Absolute folder on disk where uploads are stored |
| `MEDIA_URL` | URL prefix used to reference uploaded files in the browser |

`MEDIA_ROOT` must be **different** from `STATIC_ROOT` and from any static folder.

### Model fields

```python
# blog/models.py
class Post(models.Model):
    title = models.CharField(max_length=200)
    cover = models.ImageField(upload_to="covers/%Y/%m/", blank=True)
    attachment = models.FileField(upload_to="attachments/", blank=True)
```

- `ImageField` requires the Pillow package: `pip install Pillow`.
- `upload_to` is a folder **inside** `MEDIA_ROOT`. It can contain date codes such as `%Y/%m/`.
- Only a **relative path** is stored in the database; the file itself lives on disk (or in a storage backend, Section 14.4).

### Custom upload paths

Pass a function to `upload_to` to build paths from the object:

```python
import uuid
from pathlib import Path


def post_cover_path(instance, filename):
    ext = Path(filename).suffix.lower()
    return f"covers/{instance.author_id}/{uuid.uuid4().hex}{ext}"


class Post(models.Model):
    cover = models.ImageField(upload_to=post_cover_path)
```

Renaming uploads with a random name is a good habit: it avoids collisions and prevents unsafe or confusing file names.

### Serving media during development

Django does **not** serve media files automatically. Add this to the root `urls.py`, only for development:

```python
# mysite/urls.py
from django.conf import settings
from django.conf.urls.static import static

urlpatterns = [
    ...
]

if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

This helper does nothing when `DEBUG = False`, by design. In production, the web server or a storage service must serve media (Lesson 19).

### Using media in templates

```html
{% if post.cover %}
  <img src="{{ post.cover.url }}" alt="{{ post.title }}">
{% endif %}

<a href="{{ post.attachment.url }}">Download attachment</a>
```

Accessing `.url` on an empty field raises an error, which is why the `{% if post.cover %}` check matters.

### Working with files in code

```python
post.cover.name        # "covers/2026/03/photo.jpg"  (relative path)
post.cover.url         # "/media/covers/2026/03/photo.jpg"
post.cover.path        # absolute path on disk (local filesystem storage only)
post.cover.size        # bytes
post.cover.width       # images only
post.cover.height

post.cover.delete(save=False)     # remove the file from storage (and don't save the model yet)
```

### Deleting files

Deleting a model instance does **not** delete its file from storage. If you want files cleaned up, handle it yourself with a `post_delete` signal (Lesson 13) or use a package such as `django-cleanup`:

```python
@receiver(post_delete, sender=Post)
def delete_cover(sender, instance, **kwargs):
    if instance.cover:
        instance.cover.delete(save=False)
```

### Creating the upload form

Remember the three requirements from Lesson 10: `enctype="multipart/form-data"` on the form, `request.FILES` passed to the form, and a configured `MEDIA_ROOT`.

### Media security

- Validate **size** and **type** of every upload (Lesson 10).
- Never trust the uploaded file name or its `Content-Type`.
- Do not allow uploaded files to be executed by the web server. Ensure the media folder is configured to serve files only, never run scripts.
- Be careful serving user-uploaded HTML or SVG files from your main domain; they can run JavaScript in your site's context (XSS). Serve them from a separate domain or force a download.
- For private files (invoices, personal documents), do **not** place them in a public media folder. Serve them through a view that checks permissions, using `FileResponse`.

```python
from django.http import FileResponse
from django.shortcuts import get_object_or_404


@login_required
def download_invoice(request, pk):
    invoice = get_object_or_404(Invoice, pk=pk, owner=request.user)
    return FileResponse(invoice.pdf.open("rb"), as_attachment=True)
```

## 14.3 collectstatic

### The production problem

In development, `runserver` finds static files scattered across your apps and folders. In production, a real web server such as Nginx (or a CDN) should serve them quickly, and it expects them in **one folder**. The `collectstatic` command copies every static file from every app and `STATICFILES_DIRS` into a single destination.

### Configuring STATIC_ROOT

```python
# settings.py
STATIC_URL = "static/"
STATICFILES_DIRS = [BASE_DIR / "static"]
STATIC_ROOT = BASE_DIR / "staticfiles"
```

| Setting | Meaning |
|---|---|
| `STATICFILES_DIRS` | **Source** folders (where you keep your own files) |
| `STATIC_ROOT` | The **destination** folder `collectstatic` writes into |

`STATIC_ROOT` must **not** be one of the folders listed in `STATICFILES_DIRS`, and you should never edit files in it by hand because they are overwritten.

### Running it

```bash
python manage.py collectstatic
```

Useful options:

```bash
python manage.py collectstatic --noinput     # no confirmation prompt (for deployments)
python manage.py collectstatic --clear       # delete old files in STATIC_ROOT first
python manage.py collectstatic --dry-run     # show what would happen
```

The command also collects the admin's CSS and JavaScript, which is why your admin looks unstyled in production if you forget this step.

Add `staticfiles/` to your `.gitignore`: it is a build output, regenerated on every deployment.

### Serving the collected files

You have several options (full details in Lesson 19):

| Approach | Description |
|---|---|
| **Web server** (Nginx, Apache) | Point a `/static/` location at `STATIC_ROOT`; the fastest and most traditional choice |
| **WhiteNoise** | A middleware that lets your Django app serve its own static files efficiently; very popular on platforms like Heroku, Render, and Railway |
| **CDN / object storage** | Upload to Amazon S3, Google Cloud Storage, or similar, then serve through a CDN |

### WhiteNoise example

```bash
pip install whitenoise
```

```python
# settings.py
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "whitenoise.middleware.WhiteNoiseMiddleware",       # right after SecurityMiddleware
    ...
]

STORAGES = {
    "default": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "staticfiles": {"BACKEND": "whitenoise.storage.CompressedManifestStaticFilesStorage"},
}
```

### Cache busting with hashed file names

Browsers cache static files aggressively. If you update `style.css` but the browser keeps the old copy, users see a broken or outdated site. **Hashed file names** solve this: each file gets a name containing a fingerprint of its content (such as `style.55e7cbb9ba48.css`). When the content changes, the name changes, and browsers fetch the new file.

Django provides this through `ManifestStaticFilesStorage`:

```python
STORAGES = {
    "default": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "staticfiles": {"BACKEND": "django.contrib.staticfiles.storage.ManifestStaticFilesStorage"},
}
```

Your templates still use `{% static 'css/style.css' %}`; Django substitutes the hashed name automatically using a manifest file created by `collectstatic`.

With manifest storage and `DEBUG = False`, referencing a static file that does not exist raises an error. This is a feature: it catches typos before users do. It also means you must run `collectstatic` before running tests or the site with `DEBUG = False`.

### A typical deployment step

```bash
python manage.py migrate --noinput
python manage.py collectstatic --noinput
```

## 14.4 Storage backends

### What is a storage backend?

A **storage backend** is the class that decides *where and how* files are saved and read. Django uses one for **uploaded files** (called `"default"`) and one for **static files** (called `"staticfiles"`). Swapping the backend lets you move files from your server's disk to cloud storage without changing your models or templates.

### The STORAGES setting

Since Django 4.2, backends are configured in a single dictionary:

```python
# settings.py
STORAGES = {
    "default": {
        "BACKEND": "django.core.files.storage.FileSystemStorage",
    },
    "staticfiles": {
        "BACKEND": "django.contrib.staticfiles.storage.StaticFilesStorage",
    },
}
```

(Older projects use `DEFAULT_FILE_STORAGE` and `STATICFILES_STORAGE`, which are deprecated and removed in recent releases.)

### Built-in backends

| Backend | Purpose |
|---|---|
| `FileSystemStorage` | Stores uploaded files in `MEDIA_ROOT` (the default) |
| `StaticFilesStorage` | Default for static files |
| `ManifestStaticFilesStorage` | Static files with content-hashed names |
| `InMemoryStorage` | Keeps files in memory; handy in tests |

### Cloud storage with django-storages

Local disks are a problem when you run several servers, or on platforms with temporary file systems (such as Heroku or most container hosts), because uploaded files would vanish or exist on only one machine. The solution is to put media in object storage.

The `django-storages` package supports Amazon S3, Google Cloud Storage, Azure Blob Storage, and others.

```bash
pip install django-storages boto3
```

```python
# settings.py (Amazon S3 example)
import os

STORAGES = {
    "default": {
        "BACKEND": "storages.backends.s3.S3Storage",
        "OPTIONS": {
            "bucket_name": os.environ["AWS_STORAGE_BUCKET_NAME"],
            "region_name": "us-east-1",
        },
    },
    "staticfiles": {
        "BACKEND": "django.contrib.staticfiles.storage.StaticFilesStorage",
    },
}

AWS_ACCESS_KEY_ID = os.environ["AWS_ACCESS_KEY_ID"]
AWS_SECRET_ACCESS_KEY = os.environ["AWS_SECRET_ACCESS_KEY"]
```

With this in place, `ImageField` and `FileField` upload to S3, and `.url` returns the bucket URL. Your models and templates remain unchanged. Keep credentials in environment variables (Lesson 17, Lesson 18).

### Private files and signed URLs

Cloud storage can generate **temporary signed URLs** so private files are accessible only for a short time. In `django-storages` for S3 this is controlled by options such as `querystring_auth` (on by default) and `querystring_expire`. This is far safer than making a bucket publicly readable.

### Different storage per field

A field can use its own storage instead of the default:

```python
from django.core.files.storage import FileSystemStorage
from django.conf import settings

private_storage = FileSystemStorage(location=settings.BASE_DIR / "private_files")


class Invoice(models.Model):
    pdf = models.FileField(upload_to="invoices/", storage=private_storage)
```

`storage` may also be a callable that returns a storage instance, which lets the choice depend on settings.

### Writing a custom storage

For unusual needs, subclass `django.core.files.storage.Storage` and implement the required methods:

```python
from django.core.files.storage import Storage
from django.utils.deconstruct import deconstructible


@deconstructible
class MyStorage(Storage):
    def _open(self, name, mode="rb"): ...
    def _save(self, name, content): ...
    def exists(self, name): ...
    def url(self, name): ...
    def delete(self, name): ...
```

### Using storage directly

```python
from django.core.files.base import ContentFile
from django.core.files.storage import default_storage

path = default_storage.save("notes/hello.txt", ContentFile(b"Hello"))
default_storage.exists(path)
default_storage.url(path)
with default_storage.open(path) as f:
    print(f.read())
default_storage.delete(path)
```

### Testing with storage

In tests, avoid writing real files into your media folder. Use a temporary directory or the in-memory backend:

```python
from django.test import TestCase, override_settings

@override_settings(
    STORAGES={
        "default": {"BACKEND": "django.core.files.storage.InMemoryStorage"},
        "staticfiles": {"BACKEND": "django.contrib.staticfiles.storage.StaticFilesStorage"},
    }
)
class UploadTests(TestCase):
    ...
```

### Summary

| Concern | Static files | Media files |
|---|---|---|
| Who creates them | Developers | Users |
| URL setting | `STATIC_URL` | `MEDIA_URL` |
| Dev source folders | `STATICFILES_DIRS` + app `static/` folders | n/a |
| Disk location | `STATIC_ROOT` (after `collectstatic`) | `MEDIA_ROOT` |
| Storage key in `STORAGES` | `"staticfiles"` | `"default"` |
| Served in development by | `runserver` automatically | `static()` URL helper |
| Served in production by | Web server, WhiteNoise, or CDN | Web server or cloud storage |

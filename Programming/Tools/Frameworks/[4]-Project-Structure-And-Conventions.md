*Application Structure*

# Lesson 4 - Project Structure And Conventions

When you create a new framework project, you immediately get a set of folders and files. At first they can look intimidating, but they follow patterns that repeat across almost every framework. This lesson explains what those files are for, how frameworks use conventions to reduce the amount of setup you have to write, and walks through a small complete example.

## 4.1 Anatomy of a Framework Project

Although every framework has its own details, most projects contain the same kinds of things:

```text
my-project/
├── src/ (or app/)          ← your application code
├── public/ (or static/)    ← files served as-is: images, icons, fonts
├── tests/                  ← automated tests
├── config files            ← settings for the framework and its tools
├── dependency manifest     ← the list of packages the project needs
├── .env                    ← environment-specific settings and secrets (not committed)
├── .gitignore              ← files Git should not track
├── README.md               ← how to install and run the project
└── build output (dist/, build/, target/ ...)  ← generated, never edited by hand
```

| Part | Purpose |
|---|---|
| **Source folder** | The code you write: pages, components, controllers, models |
| **Public / static folder** | Assets delivered directly to the user without processing |
| **Tests folder** | Automated checks that your code works (Lesson 16) |
| **Dependency manifest** | A file naming every package the project uses (Lesson 5) |
| **Config files** | Settings for the framework, language, and tools |
| **Build output** | Files generated by the build process (Lesson 17); safe to delete and regenerate |

### Real examples

Here is how that general shape looks in several well-known frameworks. You do not need to memorize these; notice the common ideas.

**Django (Python)**

```text
mysite/
├── manage.py            ← command-line entry point for the project
├── mysite/
│   ├── settings.py      ← configuration
│   ├── urls.py          ← routes
│   ├── asgi.py          ← entry points for web servers
│   └── wsgi.py
└── blog/                ← an "app" (feature module)
    ├── models.py        ← database models
    ├── views.py         ← request handlers
    └── templates/       ← HTML templates
```

**Laravel (PHP)**

```text
app/          ← models, controllers, application logic
config/       ← configuration files
database/     ← migrations and seed data
public/       ← web server entry point and assets
resources/    ← views (templates) and front-end source
routes/       ← route definitions
tests/        ← automated tests
```

**Next.js (App Router style)**

```text
app/
├── layout.js       ← shared page frame
├── page.js         ← the home page ("/")
└── about/
    └── page.js     ← the about page ("/about")
public/             ← static files
package.json        ← dependency manifest and scripts
```

In every case you can find the same three questions answered: *where do my routes live?*, *where does my logic live?*, and *where do my settings live?*

## 4.2 Configuration Files

Configuration files control how your project is built, run, and tested. They come in a handful of formats and fall into a few groups.

### Dependency manifests

The manifest lists the packages your project depends on and often contains scripts and metadata.

| Ecosystem | Manifest file |
|---|---|
| JavaScript / TypeScript | `package.json` |
| Python | `requirements.txt` or `pyproject.toml` |
| Java | `pom.xml` (Maven) or `build.gradle` (Gradle) |
| PHP | `composer.json` |
| C# | a `.csproj` file |
| Ruby | `Gemfile` |
| Dart / Flutter | `pubspec.yaml` |

A small `package.json` looks like this:

```json
{
  "name": "my-project",
  "version": "1.0.0",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest"
  },
  "dependencies": {
    "react": "^18.0.0"
  },
  "devDependencies": {
    "vite": "^5.0.0"
  }
}
```

The `scripts` section defines shortcut commands (run with `npm run dev`, for example), so everyone on the team uses the same commands.

### Framework and tool settings

These files configure the framework's behavior: `settings.py` in Django, `application.properties` or `application.yml` in Spring Boot, files inside `config/` in Laravel, `tsconfig.json` for TypeScript, or a bundler configuration file such as `vite.config.js`. Linters and formatters such as ESLint and Prettier have their own settings files too.

### Environment files

A file named `.env` stores settings that differ between machines or environments, such as a database password or an API key. These must **never be committed to version control**. Instead, projects commit a harmless template such as `.env.example`, and each developer copies it to `.env` and fills in their own values. Lesson 7 covers this in detail.

### Common formats

| Format | Looks like | Often used by |
|---|---|---|
| **JSON** | `{ "port": 3000 }` | `package.json`, `tsconfig.json` |
| **YAML** | `port: 3000` | `pubspec.yaml`, Spring Boot, CI pipelines |
| **TOML** | `port = 3000` | `pyproject.toml` |
| **XML** | `<port>3000</port>` | `pom.xml`, `.csproj` |
| **.env** | `PORT=3000` | Environment settings |
| **Code** | `PORT = 3000` | `settings.py`, `vite.config.js` |

### `.gitignore`

The `.gitignore` file lists files Git should not track, such as installed dependencies, build output, and `.env`. A typical entry list for a JavaScript project is `node_modules/`, `dist/`, and `.env`.

## 4.3 Convention over Configuration

**Convention over configuration** is a design principle: the framework assumes sensible defaults based on naming and placement, so you only have to configure things when you want to *deviate* from them. The idea was popularized by Ruby on Rails, and it is now used throughout the framework world.

### Without conventions

Imagine a framework that required you to declare everything explicitly:

```text
"The model named Article is stored in the table named articles.
 The page for /about is rendered by the file about.html.
 The controller for articles lives in the file ArticlesController."
```

You would have to write this kind of declaration hundreds of times.

### With conventions

A framework that follows conventions simply *expects* you to follow a naming rule:

- A model called `Article` is automatically linked to a database table called `articles`.
- A file placed at `app/about/page.js` automatically becomes the `/about` page.
- A controller class whose name ends with "Controller" is automatically discovered.
- A Spring Boot project that finds a database library on its classpath automatically sets up a database connection with defaults.

### File-based routing: convention in action

In frameworks like Next.js, folder structure *is* the route configuration:

```text
app/page.js              →  /
app/about/page.js        →  /about
app/blog/page.js         →  /blog
app/blog/[slug]/page.js  →  /blog/any-post-title
```

No route table is written. The convention does the work.

### Trade-offs

| Advantage | Disadvantage |
|---|---|
| Much less setup code | "Magic" can be confusing: things happen without visible code |
| Projects look alike, so new team members get oriented quickly | You must learn the conventions before they help you |
| Fewer decisions to make | Deviating from the convention can be awkward |

Frameworks sit at different points on this spectrum. Django, Rails, Laravel, Spring Boot, and Next.js lean heavily on convention. Express and Flask lean toward *explicit configuration*: you wire things together yourself, which is more typing but also more visible. When you meet something in a framework that "just works" without any visible code, a convention is probably responsible, and the documentation will name it.

## 4.4 A Simple Example Project

Let's put this together with a very small project: a **task tracker** page that shows a list of tasks. It uses Flask because it is small enough to read in one sitting, but every part has an equivalent in the other frameworks.

### Project layout

```text
taskapp/
├── app.py                  ← the application: routes and data
├── templates/
│   └── index.html          ← the HTML template for the home page
├── tests/
│   └── test_app.py         ← an automated test
├── requirements.txt        ← dependency manifest
├── .env.example            ← template for settings (copy to .env)
└── .gitignore              ← files for Git to ignore
```

### The application (`app.py`)

```python
import os

from flask import Flask, render_template

app = Flask(__name__)
app.config["DEBUG"] = os.environ.get("DEBUG", "false").lower() == "true"

TASKS = [
    {"id": 1, "title": "Learn what a framework is", "done": True},
    {"id": 2, "title": "Read about project structure", "done": False},
]


@app.route("/")
def index():
    return render_template("index.html", tasks=TASKS)
```

- `Flask(__name__)` creates the application.
- `@app.route("/")` registers `index` as the handler for the home page. This is Inversion of Control from Lesson 3: Flask decides when to call it.
- `render_template` finds `index.html` in the `templates/` folder. This is a **convention**: Flask looks for templates in a folder with that exact name.
- Configuration (`DEBUG`) comes from an environment variable rather than being written into the code.

### The template (`templates/index.html`)

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>Task Tracker</title>
  </head>
  <body>
    <h1>My Tasks</h1>
    <ul>
      {% for task in tasks %}
        <li>{{ task.title }}{% if task.done %} (done){% endif %}</li>
      {% endfor %}
    </ul>
  </body>
</html>
```

The `{% ... %}` and `{{ ... }}` markers are template syntax: the loop produces one `<li>` per task.

### The supporting files

`requirements.txt` lists what the project needs:

```text
flask
pytest
```

`.env.example` documents which settings exist, without real secrets:

```text
DEBUG=true
SECRET_KEY=change-me
```

### Following one request through the project

When a visitor opens the home page, this is what happens:

| Step | What happens | Where |
|---|---|---|
| 1 | The browser asks for `/` | Visitor's browser |
| 2 | The framework matches the URL to a route | `@app.route("/")` in `app.py` |
| 3 | Your function runs and gathers the data | `index()` in `app.py` |
| 4 | The template turns the data into HTML | `templates/index.html` |
| 5 | The framework sends the HTML back | Flask |

The page that results contains one list item for each task, with "(done)" next to completed ones:

```html
<h1>My Tasks</h1>
<ul>
  <li>Learn what a framework is (done)</li>
  <li>Read about project structure</li>
</ul>
```

This small project already shows the main ideas of the whole Topic: routing, templates, configuration through the environment, a dependency manifest, and a place for tests. Larger projects add more folders and files, but they follow the same pattern.
